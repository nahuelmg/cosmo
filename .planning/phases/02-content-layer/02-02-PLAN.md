Follow RESEARCH.md Pattern 2 ("Strict Object Schemas (Zod v4 API)") verbatim. Import only from `./shared` (helpers already live there — do NOT redefine bilingualString, smart-quote regex, photo-path rule, etc.).

```ts
import * as z from "zod";
import {
  bilingualString,
  canonicalString,
  slugString,
  optionalPhoto,
  orcidId,
} from "./shared";
```

Schemas to define:

**A. `SocialLinkSchema`** — strict object:
- `platform`: `z.enum(["twitter", "linkedin", "github", "orcid", "scholar", "website", "bluesky", "instagram"])`
- `url`: `z.url()` (Zod v4 top-level form — do NOT use `z.string().url()`)

**B. `PersonSchema`** — `z.strictObject({ ... })` (DATA-01 shape, RESEARCH.md Pattern 2):
- `slug`: `slugString` (kebab-case)
- `name`: `canonicalString` (CONTEXT.md "Canonical-only fields": person names stay in original)
- `role`: `bilingualString("role")` (e.g. { es: "Investigadora Principal", en: "Principal Investigator" })
- `category`: `z.enum(["pi", "postdoc", "phd", "undergrad", "past"])`
- `photo`: `optionalPhoto` (NO default — leave undefined when absent, see shared.ts note)
- `short_bio`: `bilingualString("short_bio")`
- `full_bio`: `bilingualString("full_bio")`
- `research_interests`: `z.array(bilingualString("research_interest")).min(1)` (at least one interest required)
- `publications_selected`: `z.array(z.string()).optional().default([])` (array of publication IDs — not parsed for existence at the Zod level; the prebuild script in Plan 05 may add cross-file validation)
- `contact`: `z.strictObject({ email: z.email().optional(), orcid: orcidId.optional(), office: z.string().optional(), scholar: z.url().optional() })` — all optional; PEOP-11 requires these surface on the individual page BUT not every person has them
- `social_links`: `z.array(SocialLinkSchema).optional().default([])`
- `years`: `z.strictObject({ start: z.number().int().min(1980).max(2100), end: z.number().int().min(1980).max(2100).optional() }).optional()` — REQUIRED for `category: "past"` (validated at array level, see below)
- `thesis_topic`: `bilingualString("thesis_topic").optional()` — used by undergrads (PEOP-04: "photo, name, thesis topic")
- `current_position`: `bilingualString("current_position").optional()` — used by past members (PEOP-05: "name, role, years, current position")

**C. `PeopleSchema`** — `z.array(PersonSchema).superRefine(...)`. Enforce three rules in one superRefine pass (RESEARCH.md "Slug Uniqueness via superRefine" extended):

1. Slug uniqueness — track `seen: Set<string>`, emit `ctx.addIssue({ code: "custom", message: \`Duplicate slug "${p.slug}"\`, path: [i, "slug"], input: p.slug })` on collision.

2. Past members must have `years.start`: if `p.category === "past"` and `!p.years?.start`, emit `ctx.addIssue({ code: "custom", message: "past members must specify years.start", path: [i, "years"], input: p.years })`. This prevents a past entry rendering on the People page with no year range.

3. Undergrads must have `thesis_topic`: if `p.category === "undergrad"` and `!p.thesis_topic`, emit `ctx.addIssue({ code: "custom", message: "undergrads must specify thesis_topic (both es and en)", path: [i, "thesis_topic"], input: p.thesis_topic })`. This matches PEOP-04.

**D. Types:**
```ts
export type Person = z.infer<typeof PersonSchema>;
export type People = z.infer<typeof PeopleSchema>;
```

Do NOT add `.strict()` chains. Do NOT use `zod-to-json-schema`. Do NOT import from `"zod/v4"`.

Store paths WITHOUT leading slash: `"people/Esteban_C.png"` NOT `"/people/Esteban_C.png"` (RESEARCH.md Pitfall #4 — the `photoPath` helper in shared.ts rejects leading `/`).

**Bilingual fields** — every user-visible text must have both `{ "es": "...", "en": "..." }` both non-empty and smart-quote-free. Straight quotes only. If writing dialogue-style prose, use `"..."` straight double quotes or `'...'` straight single quotes. Spanish apostrophe in names (D'Angelo) is fine — U+0027 straight apostrophe is NOT caught by the smart-quote regex.

**Required per-category prose** (draft in a credible Argentine cosmology tone — realistic research areas: dark matter, gravitational waves, CMB, large-scale structure, N-body simulations, AI/ML for astrophysics):

- **PIs** — role like "Investigador/a Principal" / "Principal Investigator". `short_bio` 1-2 sentences. `full_bio` 2-3 paragraphs with institutional context (UBA, FCEN, CONICET, department — e.g. Depto. de Física / IFIBA / IAFE). `research_interests` 3–5 bullets (bilingual each). `contact.email`, `contact.orcid`, `contact.office` present. `contact.scholar` optional. `social_links` 1–2 entries typical.
- **Postdocs** — role "Postdoc" / "Postdoctoral Researcher". Similar depth.
- **PhDs** — role "Estudiante de Doctorado" / "PhD Student". Slightly shorter full_bio (2 paragraphs). `research_interests` 2–3 bullets. `contact.email` + `contact.orcid` typically.
- **Undergrads** — role "Estudiante de Grado" / "Undergraduate Student". `thesis_topic` REQUIRED (bilingual, 1–2 line description). Other fields can be minimal — `short_bio` brief, `full_bio` 1 paragraph, `research_interests` 1–2 bullets, contact optional.
- **Past members** — role e.g. "Ex-Doctorado" / "Former PhD Student". `years: { start: 2018, end: 2023 }` REQUIRED. `current_position` bilingual REQUIRED (e.g. "Postdoc at Max Planck Institute, Heidelberg"). Bios brief.

Plan 03 creates `content/publications.json`; cross-file ID validation is NOT required for this plan. If you include IDs here, use simple lowercase-kebab-case strings that Plan 03 can match when it writes publications.

**Slugs** — kebab-case, derived from the name (e.g. `"ana-maria-torres"`). Must be unique. Slugs are what show in URLs (`/people/ana-maria-torres`) so prefer legible forms over opaque identifiers.

**File format** — valid JSON (NO comments, NO trailing commas). Pretty-printed with 2-space indent. No `$schema` key in the array root (RESEARCH.md "Why `.vscode/settings.json` over `$schema`").

**Length guidance** — realistic is NOT minimal. A PI's full_bio should read like a real institutional-website bio (2–3 paragraphs, ~120–200 words per locale). Don't skimp on prose. The file may grow past 300 lines; that's fine for realism.

**Smart-quote guard** — before finalising, ctrl-F for `"`, `"`, `'`, `'` (U+201C, U+201D, U+2018, U+2019). None may appear in any field. The validate script will catch them at build but catching now avoids a Plan 05 false-red.

```ts
import rawPeople from "../../../content/people.json";
import { PeopleSchema, type Person } from "../schemas/people.schema";
import { localize, type Locale } from "../schemas/shared";

// Parse once at module load. If invalid, Next.js build throws here with the Zod error.
// This is also how DATA-07 manifests at the module-import layer (the prebuild script
// in Plan 05 is the first line of defence; this parse is the second).
const people: Person[] = PeopleSchema.parse(rawPeople);
```

Exports required:

1. **`getPeople(): Person[]`** — returns the full parsed array, in authoring order.

2. **`getPeopleByCategory(category: Person["category"]): Person[]`** — filter by category. Used by Phase 4 People page to split into PIs / Postdocs / PhDs / Undergrads / Past sections.

3. **`getPersonBySlug(slug: string): Person | undefined`** — single-lookup. Used by `/people/[slug]` pages.

4. **`getLocalizedPerson(slug, locale)`** — returns a Person-shaped object with every bilingual field resolved to a plain string via `localize()`. Shape:

```ts
export function getLocalizedPerson(slug: string, locale: Locale) {
  const p = getPersonBySlug(slug);
  if (!p) return undefined;
  return {
    ...p,
    role: localize(p.role, locale),
    short_bio: localize(p.short_bio, locale),
    full_bio: localize(p.full_bio, locale),
    research_interests: p.research_interests.map((ri) => localize(ri, locale)),
    thesis_topic: p.thesis_topic ? localize(p.thesis_topic, locale) : undefined,
    current_position: p.current_position ? localize(p.current_position, locale) : undefined,
  };
}
```

5. **`getLocalizedPeople(locale: Locale)`** — same idea but maps across all people, returning locale-resolved shapes. Phase 4's People page list will consume this so it doesn't have to localize in the component.

Return types — use inferred types from `typeof getLocalizedPerson` if explicit types become verbose; don't hand-roll a `LocalizedPerson` interface unless Phase 4 needs to import it.

**Why static import and not `await import()`** (RESEARCH.md Pattern 3, Anti-Patterns): dynamic import forces per-request evaluation in Server Components, defeating SSG (PERF-01). The path `../../../content/people.json` resolves at build time because `resolveJsonModule: true` is already set in `tsconfig.json` (verified in Plan 01-01).

**Import assertion syntax** — Next.js 16 + TypeScript 5 support both the legacy `import x from "./y.json"` and the newer `import x from "./y.json" with { type: "json" }`. Use the legacy form (no `with` clause) — it's what `resolveJsonModule` enables by default. If TypeScript complains, fall back to `with { type: "json" }`.
