Note: importing `.ts` from `.mjs` works because tsx registers an ESM loader that strips types on the fly. If tsx complains about `.ts` extension in the import path, fall back to `.js` extension (TypeScript's NodeNext resolution treats `.js` as the importable form of `.ts` files).

**Constants:**

```js
const ROOT        = new URL("..", import.meta.url).pathname;
```

**Loader helper:**

```js
function loadJSON(filename) {
  const full = join(CONTENT_DIR, filename);
  try {
    return JSON.parse(readFileSync(full, "utf-8"));
  } catch (e) {
    return { __loadError: `Could not parse ${filename} as JSON: ${e.message}` };
  }
}
```

**File-grouped error formatter** (CONTEXT.md "Error message format": `file → JSON path → expected/received`, multi-issue grouped by file):

```js
function formatPath(pathArr) {
  if (pathArr.length === 0) return "(root)";
  return pathArr.map((p) => (typeof p === "number" ? `[${p}]` : `.${p}`)).join("");
}

function formatZodError(filename, error) {
  const lines = [`\n  ${filename}`];
  for (const issue of error.issues) {
    lines.push(`  └─ ${formatPath(issue.path)}`);
    lines.push(`     ${issue.message}`);
    if ("received" in issue && issue.received !== undefined) {
      lines.push(`     Received: ${JSON.stringify(issue.received)}`);
    }
  }
  return lines.join("\n");
}

function formatPhotoError(filename, pathStr, relativePath) {
  return [
    ``,
    `  ${filename}`,
    `  └─ ${pathStr}`,
    `     Photo not found: public/${relativePath}`,
  ].join("\n");
}
```

**Main validation flow:**

```js
const errors = [];

const files = [
  { name: "people.json",        schema: PeopleSchema },
  { name: "publications.json",  schema: PublicationsSchema },
  { name: "research.json",      schema: ResearchSchema },
  { name: "journal-club.json",  schema: JournalClubSchema },
  { name: "outreach.json",      schema: OutreachSchema },
];

// 1. Load + parse each file
for (const { name, schema } of files) {
  const raw = loadJSON(name);
  if (raw.__loadError) {
    errors.push(`\n  ${name}\n  └─ (parse)\n     ${raw.__loadError}`);
    continue;
  }
  const result = schema.safeParse(raw);
  if (!result.success) {
    errors.push(formatZodError(name, result.error));
  }
}

// 2. Photo existence check for people.json (only content with photo fields in v1)
const rawPeople = loadJSON("people.json");
if (Array.isArray(rawPeople)) {
  rawPeople.forEach((person, i) => {
    if (person && typeof person.photo === "string" && person.photo.length > 0) {
      const full = join(PUBLIC_DIR, person.photo);
      if (!existsSync(full)) {
        errors.push(formatPhotoError("people.json", `[${i}].photo`, person.photo));
      }
    }
  });
}

// 3. Exit
if (errors.length > 0) {
  console.error("\n✖ Content validation failed\n");
  for (const e of errors) console.error(e);
  console.error("");
  process.exit(1);
}

console.log("✔ Content validation passed (5 files, all entries parsed, all photos exist)");
process.exit(0);
```

**Why photo check is OUTSIDE the Zod parse** (RESEARCH.md Anti-Patterns + Pitfall: "Zod `.refine()` for photo existence"): Zod's `parse()` is synchronous. `fs.existsSync` would work inside `.refine()` but couples filesystem state to the schema — the schema becomes non-pure. Keeping photo check as a post-parse step (a) matches how Plan 01's `photoPath` helper was written (no `.refine` for existence), (b) gives a clearly separate error category with its own error message format, and (c) lets the people schema be reused in other contexts (e.g. hypothetical test harness) without filesystem dependencies.

**Why `existsSync` and not `access`:** synchronous is fine in a prebuild script (Node 20 is single-threaded here, no event-loop concern). `existsSync` returns boolean directly without promise plumbing.

**Note on `.ts` import extensions from `.mjs`:** Per RESEARCH.md Open Question #1, this project uses `tsx` (confirmed added in Plan 01's devDeps). The script will be run with `node --import tsx/esm`, which registers tsx's ESM loader. tsx accepts `.ts` extensions in `import` specifiers from `.mjs` files. If the runtime rejects, change the schema import paths to use `.js` extension — Node's experimental TypeScript resolution prefers `.js` as the "importable form" of `.ts`. Test both and commit the working variant.

**Script:**

```js
// scripts/generate-schemas.mjs
import { writeFileSync } from "node:fs";
import { join } from "node:path";
import * as z from "zod";

import { PeopleSchema } from "../src/content/schemas/people.schema.ts";
import { PublicationsSchema } from "../src/content/schemas/publications.schema.ts";
import { ResearchSchema } from "../src/content/schemas/research.schema.ts";
import { JournalClubSchema } from "../src/content/schemas/journal-club.schema.ts";
import { OutreachSchema } from "../src/content/schemas/outreach.schema.ts";

const ROOT        = new URL("..", import.meta.url).pathname;
const CONTENT_DIR = join(ROOT, "content");

function writeSchema(zodSchema, filename) {
  // target: 'draft-07' — VS Code fully supports Draft 7 (RESEARCH.md Pitfall #2).
  // Zod v4's default is Draft 2020-12, which VS Code has only "limited support" for.
  const jsonSchema = z.toJSONSchema(zodSchema, { target: "draft-07" });
  jsonSchema["$schema"] = "http://json-schema.org/draft-07/schema#";
  const outPath = join(CONTENT_DIR, filename);
  writeFileSync(outPath, JSON.stringify(jsonSchema, null, 2) + "\n", "utf-8");
  console.log(`  wrote ${filename}`);
}

console.log("Generating content JSON Schemas (draft-07 for VS Code compatibility)...");
writeSchema(PeopleSchema,       "people.schema.json");
writeSchema(PublicationsSchema, "publications.schema.json");
writeSchema(ResearchSchema,     "research.schema.json");
writeSchema(JournalClubSchema,  "journal-club.schema.json");
writeSchema(OutreachSchema,     "outreach.schema.json");
console.log("Done.");
```

**Why `draft-07` specifically** (RESEARCH.md Pitfall #2): VS Code's JSON language server fully supports Drafts 4 through 7. Draft 2020-12 has "limited support" — in practice, `allOf`/`oneOf`/`if`/`then` may partially work but required-field highlighting breaks. Zod v4's default target is 2020-12. Always pass `{ target: "draft-07" }` for any schema consumed by VS Code.

**Why `$schema` URI in the generated output:** JSON-Schema-validating IDEs use the `$schema` key to pick validation semantics. Draft 7's URI is `http://json-schema.org/draft-07/schema#`. Setting this explicitly means the file is portable to any Draft 7-aware tool, not just VS Code.

Three manual verifications needed — each checks a different aspect of the DATA-07 / DATA-08 maintainer experience.

**Verification 1 — CLI error format on seeded violation (DATA-07, CONTEXT.md error format):**

1. Open `content/publications.json` in your editor.
2. Introduce a smart quote somewhere in a `title` field — replace a straight `"` with a curly `"` or `"` (U+201C or U+201D). Example: change `"The Λ-CDM Tension"` to `"The Λ-CDM "Tension""` with typographic quotes.

   Wait — titles are canonical (no smart-quote rejection). Use a DIFFERENT seed:

   **Option A (smart quote in a bilingual field):** Edit `content/people.json`. Find any person's `short_bio.es` value. Replace a straight `"` in the string with `"`. Example: change `"Trabajo sobre \"materia oscura\""` to `"Trabajo sobre "materia oscura""` (curly quotes).

   **Option B (missing photo):** Edit `content/people.json`. Find any person entry with a `photo` field. Change the filename to a non-existent file, e.g. `"photo": "people/Esteban_C.png"` → `"photo": "people/Does_Not_Exist.png"`.

   **Option C (unknown field):** Edit any content JSON. Add a top-level key to a random entry, e.g. `"affilation": "Typo"` (misspelled "affiliation"). `z.strictObject()` rejects unknown keys.

   **Option D (missing locale):** Edit `content/people.json`. Remove the `en` key from any `bilingualString` field, leaving only `es`.

   Pick TWO of these four seeds. Apply ONE at a time to minimise confusion.

3. Run `pnpm build`. Expected:
   - Command exits with code 1.
   - stderr shows `✖ Content validation failed`.
   - The error block is grouped under the filename (e.g. `people.json`).
   - A path like `[3].short_bio.es` or `[3].photo` or `[3].affilation` appears.
   - A clear human-readable message describes what went wrong (smart quote / photo not found / unknown key / missing locale).
   - Next.js `next build` does NOT run (prebuild short-circuited it).

4. Revert the seeded change. Run `pnpm build` again. Expected: succeeds.

5. Repeat with a second seed (different failure category). Confirm the error format stays grouped-by-file.

**Verification 2 — VS Code IntelliSense (DATA-08):**

1. Open `content/people.json` in VS Code.
2. Position cursor inside one of the person entries. Add a new key by typing `"` — VS Code's IntelliSense dropdown should suggest valid keys from the schema (slug, name, role, category, photo, short_bio, full_bio, etc.).
3. Introduce a DELIBERATE invalid value (do NOT save — just observe IntelliSense):
   - Type `"category": "bogus"` — should get a red squiggle: "Value is not accepted. Valid values: ..." (enum list).
   - Type `"photo": "/people/Foo.png"` — should get a red squiggle (leading slash refinement).
   - Type `"slug": "Foo Bar"` — should get a red squiggle (kebab-case regex).
