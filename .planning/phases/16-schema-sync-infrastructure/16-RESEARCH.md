## Summary

**Primary recommendation:** Make all schema changes first (SCHEMA cluster), then add CLI + dedup logic (DEDUP + CLI cluster), then regenerate JSON Schema and wire CI. Commit after each cluster so TypeScript stays green throughout.

**Simpler approach (recommended):** Implement `dedupByDoi` as an independent function (like `dedupByArxivId`) that takes a `Publication[]` sorted by source priority (inspire first, orcid second, arxiv last) and dedups by normalized DOI. Run it before the main sort, then sort the deduped output. This means:

1. Concatenate `[...manual, ...allInspire, ...allOrcid, ...allArxiv]` (source-priority order)
2. Apply arXiv-ID dedup (existing `dedupByArxivId`)
3. Apply DOI dedup (new `dedupByDoi`) — counts dropped entries as `dedupedCount`
4. Sort (existing sort logic in `mergePublications`)

The `mergePublications` function signature needs extending to accept `orcidEntries`. It is also used in tests — tests need updating.

### DEDUP Cluster (DEDUP-01..05)

**New function needed: `dedupByDoi`**

```typescript
/**
 * Normalize a DOI for comparison: lowercase, strip doi.org prefix variants, trim whitespace.
 */
export function normalizeDoi(doi: string): string {
  return doi
    .toLowerCase()
    .replace(/^https?:\/\/(dx\.)?doi\.org\//, "")
    .trim();
}

/**
 * Cross-source DOI dedup. Input must be ordered by source priority (high → low).
 * Returns [deduped array, count of dropped duplicates].
 * Entries without DOI pass through unchanged (DEDUP-04: fall through to arXiv-ID dedup upstream).
 */
export function dedupByDoi(entries: Publication[]): [Publication[], number] {
  const seen = new Map<string, Publication>(); // normalizedDoi → winner
  const out: Publication[] = [];
  let dropped = 0;
  for (const p of entries) {
    if (!p.doi) {
      out.push(p); // no DOI — pass through
      continue;
    }
    const key = normalizeDoi(p.doi);
    if (seen.has(key)) {
      dropped++;
      continue; // lower-priority duplicate dropped
    }
    seen.set(key, p);
    out.push(p);
  }
  return [out, dropped];
}
```

**Source priority order for input to `dedupByDoi`:** The function relies on input being ordered by priority. Since `mergePublications` concatenates (manual + inspire + orcid + arxiv) and THEN sorts by year/arXiv-ID, the sort scrambles the source order. **Solution:** Run DOI dedup BEFORE the sort, on the concatenated-but-unsorted list. The final sort is applied after dedup.

**Revised pipeline in `main()`:**
```typescript
// 1. Intra-source dedup by arXiv ID
const allInspire = dedupByArxivId(memberResults.flatMap(r => r.inspirePubs));
const allOrcid   = dedupByArxivId(memberResults.flatMap(r => r.orcidPubs));
const allArxiv   = dedupByArxivId(memberResults.flatMap(r => r.arxivPubs));
const manualEntries = readManualEntries();

// 2. Concatenate in source-priority order (for first-seen-wins dedup)

// 3. Cross-source dedup by arXiv ID (catches same paper from inspire + arxiv feed)

// 4. Cross-source dedup by DOI (new Phase 16)

// 5. Sort deterministically

const merged = postDoiDedup;
```

This avoids changing `mergePublications` signature significantly — or alternatively `mergePublications` is extended to accept `orcidEntries` and returns the sorted array (still no dedup in mergePublications).

**DEDUP-04 (entries without DOI):** The `dedupByDoi` function above passes through entries without DOI, so they remain subject to arXiv-ID dedup (step 3) and the `p.id` fallback already in `dedupByArxivId`. This requirement is automatically satisfied.

## Risks / Gotchas

### Risk 1: `content/publications.json` fails `validate-content` after schema change
**Root cause:** Adding required `orcid` and `deduped` to `counts` in the Zod schema means the existing JSON (which lacks these fields) fails Zod validation. The prebuild hook (`validate-content`) runs before build, so `pnpm build` will fail.
**Mitigation:** Either (a) make both fields optional in the schema, or (b) manually add `"orcid": 0, "deduped": 0` to `content/publications.json`'s `_meta.counts` in the same commit that updates the schema. Option (b) is recommended — it keeps the schema clean (no optionals for fields that are always written by the script).

### Risk 2: `mergePublications` signature change breaks existing tests
**Root cause:** `mergePublications` currently takes `(manual, inspire, arxiv)`. Adding `orcid` requires updating its signature.
**Mitigation:** Add `orcidEntries: Publication[] = []` as a parameter with a default empty array — this is backward compatible with existing tests that don't pass it. Or update the tests explicitly (3 test cases).

### Risk 3: DOI normalization regex must handle edge cases
**Current state:** DOIs stored in the system are "bare" (no prefix) per `doiId` regex in `shared.ts`. However, InspireHEP sometimes returns DOIs with capitalization. The `normalizeDoi` function should lowercase. The regex in `shared.ts` is case-insensitive (`/i` flag), so DOIs like `10.1103/PhysRevD.108.103512` are valid and stored as-is.
**Action:** `normalizeDoi` must lowercase before comparing: `doi.toLowerCase().trim()`. Prefix stripping is defensive (for future ORCID data) since current data has bare DOIs.

### Risk 4: `PublicationSchema` uses `z.strictObject()`, but `source` enum is not `z.strictObject`'s concern
**Non-issue:** `z.strictObject` rejects extra keys, not missing enum values. Adding `"orcid"` to the enum is safe and non-breaking for existing data (existing entries have `"manual"`, `"inspirehep"`, `"arxiv"` which remain valid).

### Risk 5: The `sources` array in `_meta` uses a typed const spread
**Current code:**
```typescript
sources: [
  ...(runInspire ? (["inspirehep"] as const) : []),
  ...(runArxiv   ? (["arxiv"]     as const) : []),
],
```
After adding `"orcid"` to the Zod enum, the TypeScript type of `sources` must accept `"orcid"`. The `as const` spreads produce literal types — this should work without issue as long as the Zod schema also accepts `"orcid"`. Type inference will align automatically.

### Risk 6: `dedupByDoi` must run BEFORE the sort
If `dedupByDoi` runs AFTER `mergePublications` (which sorts by year/arXiv-ID), source-priority order is lost and the wrong entry may be kept. The pipeline must concatenate in priority order FIRST, apply DOI dedup SECOND, then sort.

### Risk 7: Step summary in CI reads `tail -1 /tmp/sync-stdout.txt` for sync summary
**Current:** The step summary reads the last line of stdout. Extending the summary line to include `deduped` count will not break the CI step — it just includes more text. No change needed to the workflow.
