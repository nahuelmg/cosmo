    ### Addition B — new h2 section: `## Operational Troubleshooting` (append at end of file, before any existing footer)

    This is the DOC-02 content. Cover four concrete scenarios, matching the tone/brevity of the existing sections:

    **B.1 — Running a manual sync (workflow_dispatch)**

    When to use: you just added a new member's BAI/ORCID and don't want to wait until next Monday 06:00 UTC.

    Steps:
    1. Go to https://github.com/<owner>/<repo>/actions/workflows/sync-publications.yml (or navigate Actions tab → "Sync Publications" workflow in the left sidebar).
    2. Click the "Run workflow" dropdown (top-right, grey button).
    3. Confirm the branch is `main`, click the green "Run workflow" button.
    4. The run starts within ~15 seconds. Click it to follow the step-by-step progress.

    Cite the workflow file explicitly: `.github/workflows/sync-publications.yml` — `workflow_dispatch` is declared there alongside the weekly `schedule: cron: "0 6 * * 1"`.

    **B.2 — Reading the step summary**

    After a run completes, the "Summary" tab at the top of the run page shows a delta block. Expected shapes:

    - First run after adding a new member: `X added, 0 removed, Y unchanged` — where X is the number of new papers pulled from InspireHEP + arXiv for that member.
    - Steady-state weekly run: `0 added, 0 removed, Z unchanged` → the workflow's `jq -cS '.publications'` payload diff against HEAD detects no change, skips the commit, and the step summary notes "No changes — skipping commit" (CI-05 + CI-07).
    - New papers published that week: `N added, 0 removed, Z unchanged` → commit lands with message `chore(content): sync publications [skip ci]` (the `[skip ci]` prefix prevents the push from retriggering the workflow — CI-06).

    Warnings (non-fatal) appear in the step summary's warnings block: missing `orcid_id` for a member → "skipping arXiv for [name]: no orcid_id" (SYNC-05); 429 rate-limit retry → logged to stderr with exponential-backoff timing (SYNC-03).

    **B.3 — When the cron fails**

    If the Monday run didn't commit and Vercel didn't redeploy, GitHub Actions notifies the repo owner by email (default setting). Investigate in this order:

    1. Go to the failed run in the Actions tab. Open the failing step's log.
    2. Common failure modes:
       - **Startup BAI-format error** (`SYNC-06`): someone added a malformed `inspirehep_id` to `people.json` (e.g. `INSPIRE-00...` numeric form instead of BAI). Fix the ID in `people.json`, push, re-run.
       - **InspireHEP 429 after 3 retries** (`SYNC-03`): upstream temporarily overloaded. Wait an hour, re-run via `workflow_dispatch`. The script's `AbortSignal.timeout(10_000)` + exponential backoff handles transient 429s automatically; hitting the ceiling means real upstream pressure.
       - **arXiv Atom parse error** (`SYNC-02`): rare. `fast-xml-parser` hit an unexpected Atom entry shape. Capture the failing ORCID, open an issue pointing at `scripts/sync-publications.ts`'s `arxivEntryToPublication` function, and skip that member (`--member` flag omits them).
       - **`pnpm validate-content` gate fail** (`CI-04`): the sync wrote a JSON that doesn't pass `PublicationsSchema.safeParse`. This should be impossible because SYNC-11 runs the same validation in-memory before writing — if it happens, it's a schema-mismatch bug. Escalate.
    3. Reruns via `workflow_dispatch` are idempotent: the script preserves last-good JSON on any failure (SYNC-14), so retrying never corrupts the file.

    **B.4 — Running a dry-run locally (before pushing to main)**

    If a maintainer wants to preview the sync output without committing:

    ```bash
    pnpm sync-publications --dry-run --member <slug>
    ```

    Output goes to `scripts/tmp/sync-<slug>.json` — the real `content/publications.json` is not touched. This is the safest way to validate a new member's BAI/ORCID before merging.

    Cite the flag syntax from `scripts/sync-publications.ts`'s `parseArgs` CLI (09-01 decision: `--dry-run`, `--member <slug>`, `--no-arxiv`, `--no-inspire`, `--verbose`).
